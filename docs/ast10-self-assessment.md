# STAND as a skill: OWASP Agentic Skills Top 10 self-assessment

This page assesses STAND itself, as an installable coding-agent skill, against the ten risks of the [OWASP Agentic Skills Top 10](https://owasp.org/projects/agentic-skills-top-10) (AST10). It answers the question a reviewer asks before installing any skill, including this one ([references/frameworks.md](../references/frameworks.md) points reviewers to AST10 for that purpose).

**What this is and is not.** It is the project's own self-assessment, written by the project, of the repository state on 2026-10-04 (catalog 0.1.0, unreleased; no release tag exists). It is not an OWASP review, a certification or a claim of conformance, and OWASP does not endorse it. Where a mitigation depends on a maintainer operation, a host setting or an adopter's process, the page says so instead of counting it as in place.

**Source.** Risk identifiers and titles are taken from the AST10 project repository, [OWASP/www-project-agentic-skills-top-10](https://github.com/OWASP/www-project-agentic-skills-top-10), read at commit `d6f7d7d0de314f52a83a85d1828e06ab096e595c` (2026-08-12) on 2026-10-04, in the entry files `ast01.md` to `ast10.md`. The project is an OWASP Incubator project; its pages show version 1.0-2026 and ask for public review of the merged v1 draft, so titles and mitigations can still change. AST10 content is licensed under [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/). This page uses only its identifiers and titles and summarizes its risk descriptions in this project's own words.

## What is installed

The installed bundle is exactly `SKILL.md`, `references/`, `assets/`, `agents/`, `LICENSE`, `LICENSES/` and `THIRD_PARTY_NOTICES.md` ([install guide](install.md#what-gets-installed)). It is Markdown, YAML and license text. It ships no executable code, scripts, hooks or dependencies, needs no network access, MCP server or credentials, and its `SKILL.md` frontmatter declares only `name`, `description`, `license` and a `metadata` block with the skill and catalog versions, so it pre-approves no tools on hosts that support an `allowed-tools` field.

Two properties drive most of the exposure below:

- **It steers a coding agent's security decisions.** The skill's instructions run with whatever permissions the host coding agent already has. A tampered copy needs no code to do harm: changed text could lead the agent to weaken a control or a test in the application it is building.
- **It can load without being asked.** [agents/openai.yaml](../agents/openai.yaml) sets `allow_implicit_invocation: true` for Codex, and the `SKILL.md` description is written to match a broad range of agent-building tasks. On hosts with skill discovery, the skill can enter the context for any such task.

## Assessment

Status values: **addressed** (a mitigation is in the repository and can be checked), **partly addressed** (a mitigation exists but leaves a stated gap), **open** (no mitigation yet).

| Risk | Exposure for STAND | Mitigation and evidence | Status and remaining gap |
| --- | --- | --- | --- |
| **AST01 Malicious Skills** | A malicious fork, a look-alike repository or a tampered copy could present itself as STAND and steer coding agents toward insecure designs. The bundle carries no executable payload, so the risk is in the instruction text. | Install only the bundle from a reviewed, pinned commit and confirm the installed copy matches it ([install guide](install.md), steps 1, 3 and 4). `SKILL.md` "Always-on invariants" forbids silent weakening of controls and tests, and states that the skill grants no authority for deployment, publishing, tracker changes or messages. [SECURITY.md](../SECURITY.md) treats skill text that could weaken a control as a private security report. | Partly addressed. No signed release exists, so a user cannot verify publisher identity cryptographically; the defense is commit pinning and review. |
| **AST02 Supply Chain Compromise** | The bundle has no dependencies. The repository tooling (render and validation scripts) imports only the Python standard library and is not installed. CI uses third-party GitHub Actions. | CI runs with `contents: read`, does not persist credentials, and pins each action by full commit hash ([validate.yml](../.github/workflows/validate.yml)); Dependabot proposes action updates after a seven-day cooldown ([dependabot.yml](../.github/dependabot.yml)). Updates are installed only after reviewing the bundle diff ([install guide](install.md), step 6). | Addressed for the bundle. The distribution channel is a Git repository; there is no registry, transparency log or revocation endpoint. |
| **AST03 Over-Privileged Skills** | The skill requests no tools, credentials, network or MCP servers, but it directs a coding agent that already holds the developer's permissions to edit code, run tests and write a record. | `SKILL.md` limits that use: only identities and credentials configured for the host and task; no deployment, publishing, tracker change or message on the skill's authority; implementation scoped to the requested feature; no provisioning or reviewer simulation unasked. The NONE triage tier stops the workflow for unrelated edits. | Partly addressed. The limits are instructions to the agent, not host-enforced permissions; the host's own permission settings remain the enforcement layer. No permission manifest format exists in the Agent Skills specification to declare them. |
| **AST04 Insecure Metadata** | The frontmatter `description` decides when hosts load the skill, and `agents/openai.yaml` sets implicit invocation. Overstated or misleading metadata could cause loading in the wrong tasks or misrepresent the skill. | The validator allows only the frontmatter keys of the Agent Skills specification, checks that `name` matches the folder, limits the description to 1,024 characters and rejects angle brackets in it ([scripts/validate.py](../scripts/validate.py)). The description states the scope, the exclusions (non-LLM application security, configuring a coding assistant's own MCP servers, cosmetic edits) and that the skill is not affiliated with OWASP and not a certification. | Partly addressed. Implicit invocation is on by default for Codex; teams that want explicit invocation only can turn off discovery in the host ([install guide](install.md), step 5). The validator does not scan metadata or instruction text for hidden Unicode (tag, bidirectional or zero-width characters). |
| **AST05 Untrusted External Instructions** | Low. The skill references no remote document as instructions and fetches nothing at run time; every reference it loads is a local file in the bundle. URLs in `references/` are citations. | The `SKILL.md` workspace-trust rule states that retrieved instructions (repository files, issues, web pages, tool output) never authorize credential access, external communication or security-gate changes. Source editions are pinned in [references/frameworks.md](../references/frameworks.md). | Addressed. The standards-claims rule asks the agent to verify editions before a standards claim; if an agent reads publisher pages to do so, that text is data under the same rule. |
| **AST06 Weak Isolation** | The skill has no code to isolate, but its instructions run in the host agent's security context, like every skill. | Isolation of the coding agent is the host's configuration, outside this skill. The skill's own workspace rule asks the agent to inspect new skills, MCP servers, dependencies, hooks and CI changes before they run. | Not applicable to skill code; the host-level exposure is the host's to contain. The skill does not sandbox the coding agent it instructs. |
| **AST07 Update Drift** | An installed copy can fall behind fixes, or two copies for different hosts can diverge. | No auto-update: installation is a manual copy of a pinned commit, and updates are reviewed with `git diff` against the installed commit and the "Normative changes" in [CHANGELOG.md](../CHANGELOG.md) before reinstalling ([install guide](install.md), steps 1 and 6). The installed-copy check detects a copy that differs from the reviewed checkout, and the staged validation checks the reviewed bundle on its own (step 4). The guide asks teams with two hosts to install both copies from the same commit and update them together. Security fixes are announced through GitHub security advisories ([SECURITY.md](../SECURITY.md)). | Partly addressed. No release is tagged yet, so pinning uses a full commit hash; signed release tags are planned in the release procedure ([CONTRIBUTING.md](../CONTRIBUTING.md#releases)) but none exists. The host does not check the installed copy at load time. |
| **AST08 Poor Scanning** | Pattern-based checks cannot judge whether instruction text is safe, and this skill is almost entirely instruction text. | Every change runs the repository checks in CI (render drift, catalog and ledger rules, links that resolve inside the bundle, a staged bundle validation and unit tests). Normative changes need maintainer review ([CONTRIBUTING.md](../CONTRIBUTING.md)). | Partly addressed. These checks validate structure and consistency, not intent: nothing scans for prompt injection, hidden Unicode or instructions that weaken controls. Review is human. Adopters can run an agent-skill scanner as an additional, advisory signal. |
| **AST09 No Governance** | Without a reporting path, change control and an owner, a flaw in the skill would spread to every application built with it. | [SECURITY.md](../SECURITY.md) gives private reporting, response targets and advisory publication. [CONTRIBUTING.md](../CONTRIBUTING.md) requires a changelog entry for every catalog change, maintainer review of normative changes and Developer Certificate of Origin sign-off. The install guide asks project installations to commit the copied bundle with its source commit, so the version in use is recorded. | Partly addressed. Branch protection, required checks and sign-off enforcement are maintainer operations that this page does not verify. Keeping an organization-wide inventory of installed skills, and revoking them, is the adopting organization's work. |
| **AST10 Cross-Platform Reuse** | One bundle is installed on several hosts (Claude Code, Codex, GitHub Copilot CLI, Gemini CLI, Cursor), each with its own discovery and invocation rules. | The bundle follows the Agent Skills specification, and the validator rejects frontmatter keys outside it, so every host reads the same metadata. The only host-specific file is `agents/openai.yaml` (Codex display metadata, a default prompt and the implicit-invocation policy). The skill declares no permission manifest, so porting loses no permission metadata. | Partly addressed. The implicit-invocation setting is expressed only for Codex; on other hosts, whether the skill loads implicitly depends on host settings. The AST10 Universal Skill Format proposal is not adopted. |

## Open items

These gaps come from the table. None is a change to the skill's guidance; each is a packaging, tooling or release task:

1. Publish signed release tags, so that adopters can verify a release with `git verify-tag` instead of pinning a bare commit hash (AST01, AST07).
2. Add a hidden-character check (Unicode tag, bidirectional and zero-width characters) for `SKILL.md`, `references/`, `assets/` and `agents/` to the repository validator (AST04, AST08).
3. Decide whether implicit invocation should stay on by default for Codex, given how broadly the description matches (AST04, AST10).
4. Re-run this assessment when AST10 publishes a final v1, and on each STAND release.
