# Changelog

All notable changes to this project are documented in this file. The format is based on [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/). The catalog version follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html) with the catalog rules in [CONTRIBUTING.md](CONTRIBUTING.md#change-the-catalog). Each release lists its normative changes with the affected control IDs, and records every primary-source recheck with its date.

## [0.1.0] - Unreleased

First versioned release, and the first with a normative control catalog. Earlier revisions were unversioned guidance without stable control IDs or conformance rules, and only the invariants in `SKILL.md` were normative. Before tagging, recheck AIUC-1 against its October 15, 2026 release (see Source snapshot). Clause identifiers for compound controls (`<ID>/R<n>` labels for each obligation, a `verifies` field on each case, and a validator check that every MUST clause is covered by a case or marked inspection-only) are deferred to the next catalog version; they will start with A-06, T-12, T-17, A-12, A-25, T-01, S-05 and A-07. Until then, cases are not mapped to individual clauses.

### Normative changes

- Control catalog 0.1.0 with 78 controls across the five pillars: Scope & Stewardship S-01 to S-06, Trust & Isolation T-01 to T-27, Authority & Access A-01 to A-25, Notice & Neutralize N-01 to N-10, and Demonstrated Defenses D-01 to D-10. Each control has a statement in BCP 14 language, a rationale, applies_when conditions, a level, a default failure severity, a minimum evidence scope, ASI references, verification with a hostile case and an authorized twin, and the evidence to keep. Every hostile case and twin carries its test label `(C<n>)` in the verification text, so fixtures cite the same numbers. Every active control has a labelled authorized twin except D-08 and D-09, which are verified by inspecting a report or review record and give the reason in a `twin_exempt` field (D-02).
- Levels 1 to 3 (61, 12 and 5 controls), selected per agent context from its capability profile.
- The critical-boundary set: the 32 Level 1 controls whose default failure severity is critical. `SKILL.md` lists them as always-on invariants.
- Change triage into NONE, SCOPED and FULL tiers, with a definition of the baseline record, a compact change record of at most 12 lines plus one per routed control (counting every non-blank line the change adds to the record, fences and headings included), and a scope rule that separates assessing from implementing: FULL assesses every applicable control, but in every tier implementation stays inside the requested feature and the boundaries it creates or changes. Gaps in unchanged features are recorded as findings, and new flows, endpoints, confirmations, limits or behavior changes are owner decisions unless a critical-boundary control for the requested feature cannot otherwise be met. The routing table in `SKILL.md` Step 2 is normative as to which control IDs each trigger location routes to.
- Applicability: `provider-routing` covers remote tool servers (remote MCP servers, remote agents, third-party APIs that receive tool arguments), and `network-egress` covers calls to remote MCP servers and agents and fetches of server-supplied URLs. Reviewed, pinned descriptors count as trusted configuration only while T-18 is implemented-and-verified (evaluation rule 4).
- Conformance rules: the status enum (implemented-and-verified, implemented-but-unverified, planned, not-applicable-with-reason, failing, not-assessed), the evidence scope enum (inspection, unit, simulation, integration, isolated-runtime, deployed), conformance statements and their lapse, progress statements, the severity rubric and the release gate. A SHOULD deviation counts only when the accountable owner has recorded it. A carried-forward claim names its commit range and the change records in it. A security advisory that names a catalog version and control makes claims against that version lapse for that control until reassessed.
- Severity and release gate: a control's recorded severity is the highest of its default failure severity, any floor its statement sets, and the rubric result (D-06). The escalations that rationales used to describe are now floors in the statements of S-01, S-02, S-03, T-04, T-07, T-26, A-05, A-09, A-12 and A-22. A ready-within-scope claim also needs S-02 and S-05 implemented-and-verified where they apply, and A-12 implemented-and-verified for every confirmation surface that an applicable critical-boundary control relies on (D-06, new case D-06/C4). For a control that is not yet verified, a floor applies when the profile or register shows its precondition, for example T-07 in a multi-tenant context with memory (D-06, new case D-06/C6).
- Untrusted content by field: any free-text field written by a party other than the current principal is untrusted content wherever it enters a context, including free text inside system-of-record records (names, addresses, delivery notes, comments). A system-of-record field of a closed type (an identifier the application generated, a number, a boolean, a timestamp, or a member of a closed enumeration the application defines) is not untrusted content, whoever chose its value; where another party chose it, the value is untrusted-derived when it feeds a consequential argument (new case T-01/C10). Any string another party chose (an email address, username or external reference) is free text whatever its format validation. Results from MCP servers and other third-party tools stay untrusted in full (T-01, new cases T-01/C5 to C7). A separated planner can receive such system-of-record fields; it receives free text only by opaque reference (T-02, new case T-02/C7).
- Model-influenced process is defined (T-05, new case T-05/C8): a process that executes, interprets or loads model-chosen code, commands, modules or file contents, or whose control flow the model can direct beyond selecting a registered operation with schema-validated arguments. A dispatcher host that parses proposals only as data, and calls adapters whose credentials stay in a broker or adapter boundary, is not one. Parsing, conversion or rendering of fetched content in complex formats runs in a sandboxed worker with no route to enforcement components, not in the dispatcher host. A-01 cites the definition.
- A-06 defines designated content: an item the principal named or selected in this task, or the direct results of a retrieval whose full query the principal wrote, or reviewed and submitted in a structured field that no tainted context filled. The application records each designation before the item enters the context, and a tainted context cannot designate anything. A read-tool query has a trusted source only when it is principal-entered or a query composer derived it (a context that has read no untrusted content in this run and receives only principal turns from a channel shown to carry no pasted, uploaded or forwarded content; otherwise its query waits in a structured field for the principal to submit). A query that a tainted context composed is never sent on confirmation. A system-of-record value matches only for the field that the principal's task names for that argument, or, where the task names none, the one field the register fixes as its only permitted value, so an injected full-balance refund is untrusted-derived even where the register lists the balance as a source. Search and fetch tools expose at most L links per retrieved item (one search response or one fetched page), exempt fetches are also capped per principal per day, and the record bounds the residual channel at log2(L+1) bits per exempt fetch, per run, per day and over the retention of the most persistent secret class, against the secret classes and entropies that S-06 now records. New cases A-06/C11 to C18; A-06/C5 and C6 deny without offering a confirmation, and the URL part of A-06/C8 is now C18.
- A-08: under every option, a read-tool request that A-06 allows without confirmation (an exempt URL, or a query or URL that matches a trusted source, including a composer's query) is not a consequential effect, and under option (b) it is not a reachable effect whose destination must be fixed, so an unattended research agent can conform; a confirmation never authorizes a value that A-06 denies (new cases A-08/C5 to C7, with the A-12 markup check labelled C6).
- Trusted sources (S-05, new cases S-05/C6 and C7): a value that application code computes deterministically from trusted sources only is a trusted source. A sender's authenticated origin is a trusted source only for a response to that origin. The trigger adapter authenticates that origin before any sender-dependent policy applies (a From domain with strict DKIM or SPF alignment, signed and timestamped webhooks, and a calendar organizer only from the same calendar tenant or a message whose authenticated From equals it; DMARC authenticates the domain, never the mailbox, new cases A-19/C9 to C11); Reply-To headers, display names and addresses in the body stay untrusted-derived (A-19, new cases A-19/C6 to C8). A case requester's verified address on record is a trusted source only for a reply on that case. A-10 classes sends, defines bulk modification by a count the register sets, and keeps other external communication under A-06, A-07, A-08 and A-24 (new case A-10/C8). A destination rule that binds a reply's recipient to the authenticated trigger origin counts as fixed under A-08 option (b), which states the rule; A-10 option (c) cites it and requires every other parameter to be fixed too (new cases A-10/C9 and C10).
- Non-sensitive conversation (S-02, new cases S-02/C5 and C6): the principal's conversation counts as sensitive-data unless the principal is anonymous, nothing is retained or written to memory, no reachable tool or retrieval reads non-public data, and the context receives no data of other principals. T-17 uses the same conditions instead of a free-text reason.
- T-12 has two recorded modes per context and tool. Allowlist mode is required for sandboxes, code execution, MCP, OAuth discovery and every sensitive-data request except the next case. Public-internet mode is allowed only for search, fetch or browse tools, in contexts without sensitive-data, and in sensitive contexts only for credential-less GETs that A-06 allows (exempt under (i) to (iii), matching a trusted source such as a URL the principal entered, or confirmed as supplied or designated content) and the requests a page reached that way makes itself. It allows only https, and http where configured, on ports 443 and 80, still blocks internal, link-local and metadata addresses and redirects to them, sends no credentials, and resolves through a resolver that refuses internal names and logs queries (new cases T-12/C11 to C15). T-17 and A-06 (iii) cite it. T-17: with a delegated session or sensitive-data, each navigation is allowlisted, a link followed under the A-06 exemption from a profile that sends no session cookie or credential, or a URL that matches a trusted source or is confirmed for that exact URL, never for its origin. A URL or search query the tainted context composed is never navigated to or submitted, and typing into a page outside the allowlist counts as form submission (new cases T-17/C6 to C8). T-11: a hosted search or fetch tool whose arguments the dispatcher cannot check before sending is not enabled in a context that holds sensitive-data and can hold untrusted-input, and holding such a call for approval no longer passes T-11/C1 (new case T-11/C3).
- Fresh re-authentication (A-12, new cases A-12/C9 to C11 and C15) is a gesture an agent cannot perform, made for the values the person saw: a confirmation on a separately enrolled device that displays the action and each material value with provenance from server data, with number matching or entry of a value shown only on the application's surface; a WebAuthn variant that displays the transaction (for example Secure Payment Confirmation); or a WebAuthn assertion with user verification required, against a server-stored random challenge bound to the exact action and values, started only from the application's preview, with the residual risk that an agent-capable browser rewrites the preview recorded. Passwords and one-time codes that can be filled or read do not count. A server cannot detect an agent in the principal's own browser, so the profile records whether the principal's browser can be agent-driven (unknown counts as yes); where it can, fresh re-authentication is required for effects at or above the impact threshold the register records under S-05 (the A-14 threshold at Level 3) or registered as irreversible, and for confirmations reached through an approval link (new case A-12/C12); verification of an A-25 change always requires it. Voice and telephony confirmations are part of A-12: an application-generated prompt from server data, answered only by keypad in the application's own confirmation state on a call leg with the principal alone (new cases A-12/C13 and C14). For an agent the application operates, the confirmation surface renders outside that agent's profile, virtual machine and display. Approval and verification pages need anti-CSRF tokens and must forbid framing. A-25 relies on this definition: where the principal has no suitable authenticator, a model-proposed change does not take effect (new cases A-25/C8 to C10).
- Branches are active configuration (A-23, T-23): a branch is active configuration for every automation that runs on it. Agent credentials get no permission to change workflow definitions (no GitHub App workflows permission, no PAT workflow scope, or an equivalent rule elsewhere). Agent pushes go to a fork or to a branch namespace where no triggered workflow, including `pull_request_target`, `workflow_run` and comment-triggered workflows that run the agent's code, receives secrets, a write token, a cloud OIDC token or a runner shared with privileged jobs. Deployment and publish secrets sit in reviewer-gated or protected-branch environments. The example that called a pushed branch review-gated is removed. A-23 is the single owner of the rule against an agent changing its own configuration; T-19 refers to it, and its third case is retired, with the configuration-write cases now in A-23/C7 and C8. New cases A-23/C10 and T-23/C4 to C7; A-23/C9 rewritten.
- MCP Apps and server-supplied UI: tool calls that such UI initiates are untrusted proposals through the dispatcher (A-01, new case A-01/C4). Its messages toward model context are untrusted content (T-01). It renders in a sandboxed frame on a separate origin with a restrictive Content Security Policy (T-13, new case T-13/C7). Its UI resources and declared domains are pinned (T-18). Approval surfaces sit outside any frame it controls (A-12). Annotations and descriptor text never relax policy, even from a trusted, pinned server (T-18, new case T-18/C8).
- Retrieval, memory and models: response, prompt and semantic caches are keyed by tenant, principal and data-policy version, and serve a cached answer only to a principal entitled to every item that produced it. T-06 now also applies on `multi-tenant` (new case T-06/C5). Memory lineage survives recall and relay, and removing a member from a shared scope also purges or quarantines every derived entry (T-07, new cases T-07/C6 and C7). T-06 and T-07 tests run against the production index, store and cache engine. A model or adapter trained on one tenant's data serves only that tenant unless the data policy allows otherwise (T-25, new case T-25/C4).
- Defined terms: S-03 requires a reason for each tool, trigger or delegate at autonomy scope 3 or 4. T-15 defines its validation gate as a deterministic, logged policy check the model cannot skip (new case T-15/C12). T-20 withholds conversation, system prompt and other servers' results from sampling unless that server's policy allows the class. A-13 measures anomalies against a look-back window the register sets. A-14 sets a floor for the impact threshold (new case A-14/C6) and defines the requester and step-up authentication. N-08 exercises the incident procedure at least every 12 months and after any change to the quarantine path, instead of once per release cycle.
- Agent-to-human output (T-26, new cases T-26/C3 and C4, now tagged ASI01): output from a tainted context is marked as derived from unverified content and lists its untrusted sources, determined from taint and provenance labels. Model-produced forms, fields and commands are inert. Consequential values in structured form show their provenance and, where it exists, the system-of-record value.
- Detection and stop: N-04 adds signals for sandbox violations and blocked egress, rejected or replayed inter-agent messages, and delegations or tokens used outside their envelope, is tagged ASI03, ASI05 and ASI07, and so now lists every ASI category (new cases N-04/C2 to C5). N-05 baselines memory and index write rates and sources and is tagged ASI06 (new case N-05/C3). N-06 lets the principal who started a run stop it, and the stop reaches provider-side background responses, managed sessions, provider-executed tools, connectors and their delegated credentials (new cases N-06/C4 and C5).
- Framework text in `references/profile-and-levels.md`: a Terms table defines consequential operation and argument, trusted source, principal-entered, supplied and designated content, query composer, untrusted content, tainted context, untrusted-derived, model-influenced process, redirecting value, bulk modification and fresh re-authentication, each by reference to the control whose statement governs. The untrusted-input property carries the same field rule as T-01, and worked example 3 shows a planner that receives typed system-of-record fields only. Autonomy scopes are defined from consequential actions, and scope 3 records a maximum duration and a principal stop. `network-egress` covers a model-chosen scheme, host, port or path (a fixed-host adapter is `provider-routing`), and `retrieval` covers response, prompt and semantic caches. A second worked example shows a narrow change whose adapter lacks idempotency and records the A-05 gap as a Finding line.
- Change triage: the baseline record is a claim, read at the merge base, with the level recomputed and the highest level used; edits a change makes to the record's profile, level, status, readiness, owner or exception lines are proposals for human review. The record file is created only when the repository adopted the workflow or the user asked; otherwise the compact record goes in the report. A routed control that is not critical-boundary and whose mechanism is missing at a touched boundary is a Finding unless the diff needs the mechanism. The exemption for controls that need people or infrastructure the repository lacks applies to SCOPED and FULL alike, and a final self-check lists every unrequested behavior change. A requested review or threat model is read-only, and in interactive sessions the agent checks in before re-assessing beyond the request.
- Conformance (`references/conformance.md`): before a control is recorded implemented-and-verified, every required case is listed by label with its result and scope (claim audit). A Constrained precondition never lowers the default severity or a floor; only a recorded, verified precondition that makes the attack unreachable does. Readiness also needs every owner exception it relies on to be unexpired, and a SCOPED change rechecks the owner and the exception expiry. New validity condition 8: a human reviews the profile, the not-applicable reasons and the hostile-case and twin inventory for the critical-boundary set; a coding agent may draft a statement but never publishes one. A new section on the security record sets record confidentiality (open critical and high items by reference only where the record is readable beyond the people authorized to see them, with unknown visibility treated as public) and record and catalog integrity (the assessment commit is named, status, level and readiness lines change only through human review, and a statement made with an edited installed copy is invalid). A shared-responsibility subsection says external evidence counts only with the adopter's own cases at the adopter's evidence scope, and an attestation alone never verifies a control. The critical-boundary set excludes withdrawn controls.
- Record integrity and statements in the catalog, matching the conformance rules: a coding agent may draft a conformance or progress statement but never publishes one or records one as published (S-01, new case S-01/C4). The record names the commit of each assessment, and changes to its profile, level, status and readiness lines go through human review and are proposals until reviewed (D-03, new case D-03/C3). A readiness claim, including one a compact change record carries forward, never relies on an expired exception or an unassigned owner (D-06, new case D-06/C5). Code-owner review of security tests and policy files is required at Level 2 or above (D-07).
- Identifiers: the catalog namespace is `STAND`, and the fully qualified citation form is `STAND:A-06@0.1`. ID letters are identifiers, not abbreviations of the framework or pillar names. A change of subject, a split or a merge now deprecates the old ID with `superseded_by` and withdraws it no earlier than the next minor release (`references/profile-and-levels.md`, `catalog/ledger.json`, `CONTRIBUTING.md`).
- Twins and test labels (S-04, N-01, N-03, N-05, N-07, N-09, D-01 to D-05, D-08, D-09): new labelled twins and cases S-04/C2, N-03/C4, N-07/C2, N-09/C2, D-01/C2, D-02/C1 and C2, D-03/C2, D-04/C1 and C2, and D-05/C1 to C11 (one per matrix row; C11 is the twin). N-01/C2 and N-05/C2 are relabelled as twins. D-05 requires a scoped change to run at least the rows for the boundaries it touches. D-02 exempts inspection-only controls from the twin rule, and D-08 and D-09 state why.
- Browser and public-internet egress (T-12, T-17, A-06; new cases T-12/C16 to C18, T-17/C9 and C10). In a context with sensitive-data, the egress boundary admits a public-internet-mode request only with a single-use authorization the dispatcher issued for that exact canonical URL, bound to the run and context and checked before the hostname is resolved, or only from the dispatcher's own fetch adapter, and a browser harness intercepts every top-level navigation (address-bar entry, link clicks, script-driven location changes), form submission and typed input. Redirect hops of an authorized request, and requests a page makes itself while the agent has delivered no input to it, need no authorization of their own. Public-internet mode allows https on port 443, and http on port 80 only where configured. In such a context the agent delivers no pointer, scroll, keyboard or focus input to a page outside the allowlist, or every request that page makes after the first input is blocked; exempt links are followed by index from a tool-extracted list of at most L links, which is also how a browse tool meets the A-06 limit; and exempt or non-allowlisted pages load only in a browser context that holds no delegated session.
- MCP Apps and designation (A-01, A-06, A-07; new cases A-01/C5 and A-06/C19): a view may call only tools of its own server that the server marks callable from the app, and its messages and selections never designate content or set or widen task scope; only structured interfaces the application renders count. An item whose arrival started a triggered run with no principal in session is not designated.
- Free-text chat (T-01, A-07; new cases T-01/C8 and C9, A-07/C5 and C6): a free-text principal turn whose pasted, uploaded or forwarded spans the client does not mark taints the context it enters, and the scope derived from such a turn is confirmed by the principal whether or not the context is tainted. `references/profile-and-levels.md` defines the term and its four consequences.
- A-06 read-tool exemption (new cases A-06/C20 and C21): the per-run selection bound (the per-run cap times log2(L+1) bits) must not exceed a ceiling the owner records below the entropy of the lowest-entropy secret class the context can hold, or that class reaches the context only by opaque reference; the daily and retention-period totals are recorded as residual risk accepted under S-01. A-06/C13 states that the register allows several amount sources.
- Impact threshold and query composer (S-05, new cases S-05/C8 and C9): the register records an impact threshold for every operation that moves funds or grants access (the A-14 threshold at Level 3), which A-12 uses, and the output of a query composer is a trusted source for a read-tool query argument.
- CI caches and artifacts (T-23, new case T-23/C8): a workflow that runs the agent's code neither uses nor writes a cache that privileged workflows restore, or privileged workflows restore no caches, and artifacts from agent branches and pull requests are data, never code, build or release inputs. T-23 cites A-23 for changes to workflows, branch protection, security tests and instruction files instead of repeating the rule.
- Stop (N-06, new case N-06/C6): for a run started through an API, the principal's stop is a cancel operation on that API, and a run does not use a provider background response or managed session type the provider cannot cancel.
- Severity floors (D-06, new case D-06/C7): the floor lists in D-06 and `references/conformance.md` add T-26 and A-22 as precondition floors and S-03 as a failure floor, so every statement that sets a floor is listed.
- Case labels: a case that guidance or an adopter adds uses its own namespace, `<ID>/L<n>`, so catalog case numbers are never reused or renumbered, even before the first release. The local cases in `references/patterns.md`, `references/mcp.md` and `references/runtime-controls.md` moved to that namespace, and the voice cases became catalog cases A-12/C13 and C14.

### Changed

- Renamed the framework and skill from the working name RAISE to STAND (Secure, Trustworthy Agents by Non-negotiable Design) to avoid confusion with other RAISE frameworks.
- Renamed the five pillars so their initials spell STAND, in this order: Risk & Responsibility to Scope & Stewardship (S), Isolation & Integrity to Trust & Isolation (T), Authority & Access unchanged (A), Evidence & Evolution to Notice & Neutralize (N), and Security Verification to Demonstrated Defenses (D). ### Security

- Closed a design gap in the earlier guidance: it had no rule against untrusted content choosing recipients, destinations or consequential arguments that the caller is allowed to use. A-06, A-07, A-08, T-01 and T-02 now cover it, and all five are in the critical-boundary set.
- Values that cross a verified separation boundary (T-02) stay untrusted-derived: A-06 and A-07 also apply through a `separation-pattern+external-effect` alternative, so a well-formed value the attacker chose (another tenant's order ID, a planted address) is still checked at dispatch. A system-of-record trusted source for an object identifier is scoped to the principal or case the run acts for (S-05, A-06), so an identifier that merely exists does not match. Sensitive data now propagates between contexts like untrusted input (S-02), so the lethal trifecta cannot be split across a summarizer and a sender.
- A-24 (outbound payload checks, Level 1, critical) limits what an outbound message, comment or document carries: data a recipient or reader is not entitled to, and remote images or data-carrying links that a renderer outside the application would fetch with no click.
- A delegate's authority includes the delegating context's own ceiling in the intersection (A-15), so a grandchild cannot exceed its parent.
- A-25 (verified changes to redirecting values, Level 1, critical, in the critical-boundary set): a stored contact email or phone number, recovery channel, payout or payee account or default refund destination, webhook or callback URL, or forwarding rule that is untrusted-derived, or not already held as verified for this principal's account and the same purpose, never takes effect on in-app confirmation alone. It is verified through this principal's destination on record, or, only for a value the principal entered in a structured field, through the new destination. Completion needs a non-GET human action after fresh re-authentication as A-12 defines it, on a confirmation surface that meets A-12, so an agent that reads the inbox or drives a signed-in browser cannot complete it. Every change, including one to a value already on record, is audited and the previous destination notified. A model-invented redirecting value is denied. A one-time payment to a new account sets no redirecting value and stays with A-06, A-12 and A-13; A-13 cites A-25 as the Level 1 floor for stored payment destinations. Cases A-25/C1 to C9.
- A-06: a consequential value that matches no trusted source and occurs in no content the principal supplied or designated in this task (a value the model invented, or one found only by the run's own retrieval) is denied, and a confirmation cannot authorize it. New cases A-06/C9 and A-06/C10; A-06/C7 accepts denial as well as confirmation. An item that a trigger sender delivered is not content the principal designated, even when its arrival started the run, so a value found only there is denied unless it matches a trusted source.
- A-12: a confirmation is accepted only from the session to which the server rendered its preview (recorded server-side), or from another session of the approver after fresh re-authentication to which the preview is rendered again; an approval link sent by email, push or chat opens such a preview and never confirms on its own (MUST, new cases A-12/C6 to A-12/C8). The A-25 verification page is a confirmation surface under A-12. It sits in A-12 rather than A-11 because the holder of another session already has the principal's authority, so the harm is presentation integrity, rated at A-12's default severity.
- Added coverage for surfaces the earlier guidance barely addressed: MCP token handling, descriptors, local servers, sampling and elicitation (A-16, T-18, T-19, T-20), and browser and computer-use agents (T-17).
- T-27 (per-tenant kernel isolation for code execution, Level 1, high): code executed for more than one tenant never shares a kernel across tenants and runs in a fresh sandbox per tenant and session, because every principal is a potential attacker against the other tenants.
- A-06: a URL is exempt from confirmation only when it appears verbatim in a public web result whose own request passed A-06, within a per-run and per-principal daily cap set in trusted configuration, from an item that exposes at most L links, as a credential-less GET through T-12 in either mode. URLs that appear only in output reflecting model input (code-execution output, echoing tools, agent-written notes or memory), and capability links in the principal's own mail or documents, stay consequential, and the record bounds the residual channel by the cap.
- T-12: allowlisted hosts that accept authenticated writes from any account (code hosts, registries, provider and storage APIs) are confined to the operator's account, limited to read-only methods or mirrored, so injected content cannot push context data into an attacker's account under the attacker's own token. File paths are opened relative to a trusted root handle (A-02), which closes the symlink-swap race between check and open.
- T-15: a sandbox whose workspace is later used on the host cannot write files that host tools execute (git hooks and configuration, editor tasks, `.envrc`, devcontainer and CI definitions, agent instruction and MCP configuration). A-09 and T-23 cite the rule.
- T-18: the descriptor pin covers every server-supplied field that reaches the model or the reviewer, including server instructions, tool titles, model-visible `_meta`, and prompt and resource descriptors; instructions from an unpinned server never go in system or developer position. T-01 treats pinned descriptors as trusted only while T-18 is implemented-and-verified.
- A-10: publication, sharing, sending and access grants can no longer satisfy the guard as "reversible by design". A-11 binds approvals to the requesting principal, run and step. A-18 requires a non-exportable proof-of-possession key that no model-influenced process can read.
- T-10 and A-24 cover free-text tool arguments sent to remote tool servers, and T-10 also applies through `sensitive-data+mcp`. T-02 credits context minimization only when a separate context translates untrusted content into typed values first. T-03 keeps RGI emoji tag sequences (subdivision flags) and removes every other tag sequence.
