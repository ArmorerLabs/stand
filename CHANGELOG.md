# Changelog

All notable changes to this project are documented in this file. The format is based on [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/). The catalog version follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html) with the catalog rules in [CONTRIBUTING.md](CONTRIBUTING.md#change-the-catalog). Each release lists its normative changes with the affected control IDs, and records every primary-source recheck with its date.

## [0.1.0] - Unreleased

First versioned release, and the first with a normative control catalog. Earlier revisions were unversioned guidance without stable control IDs or conformance rules, and only the invariants in `SKILL.md` were normative. Before tagging, recheck AIUC-1 against its October 15, 2026 release (see Source snapshot).

### Normative changes

- Control catalog 0.1.0 with 78 controls across the five pillars: Risk & Responsibility R-01 to R-06, Authority & Access A-01 to A-25, Isolation & Integrity I-01 to I-27, Security Verification S-01 to S-10, and Evidence & Evolution E-01 to E-10. Each control has a statement in BCP 14 language, a rationale, applies_when conditions, a level, a default failure severity, a minimum evidence scope, ASI references, verification with a hostile case and an authorized twin, and the evidence to keep. Every hostile case and twin carries its test label `(T<n>)` in the verification text, so fixtures cite the same numbers.
- Levels 1 to 3 (61, 12 and 5 controls), selected per agent context from its capability profile.
- The critical-boundary set: the 32 Level 1 controls whose default failure severity is critical. `SKILL.md` lists them as always-on invariants.
- Change triage into NONE, SCOPED and FULL tiers, with a definition of the baseline record, a compact change record of at most 12 lines plus one per routed control (counting every non-blank line the change adds to the record, fences and headings included), and a scope rule that separates assessing from implementing: FULL assesses every applicable control, but in every tier implementation stays inside the requested feature and the boundaries it creates or changes. Gaps in unchanged features are recorded as findings, and new flows, endpoints, confirmations, limits or behavior changes are owner decisions unless a critical-boundary control for the requested feature cannot otherwise be met. The routing table in `SKILL.md` Step 2 is normative as to which control IDs each trigger location routes to.
- Applicability: `provider-routing` covers remote tool servers (remote MCP servers, remote agents, third-party APIs that receive tool arguments), and `network-egress` covers calls to remote MCP servers and agents and fetches of server-supplied URLs. Reviewed, pinned descriptors count as trusted configuration only while I-18 is implemented-and-verified (evaluation rule 4).
- Conformance rules: the status enum (implemented-and-verified, implemented-but-unverified, planned, not-applicable-with-reason, failing, not-assessed), the evidence scope enum (inspection, unit, simulation, integration, isolated-runtime, deployed), conformance statements and their lapse, progress statements, the severity rubric and the release gate. A SHOULD deviation counts only when the accountable owner has recorded it. A carried-forward claim names its commit range and the change records in it. A security advisory that names a catalog version and control makes claims against that version lapse for that control until reassessed.

- `references/conformance.md`: normative language, evidence scope and status enums, conformance and progress statements, the nature of a claim, the severity rubric and release gate, and the critical-boundary set.
- `references/mcp.md` and `references/patterns.md`: non-normative MCP guidance and implementation patterns, keyed by control ID.
- Engineering mappings from each control to AIUC-1, NIST AI RMF 1.0 and NIST AI 600-1, and cross-references to OWASP AISVS 1.0 by identifier, each with a relation and a justification. They are not certification or conformance claims.
- `docs/install.md` with installation steps per coding-agent host.
- `evals/cases.json`: machine-readable evaluation cases, with a pre-registered acceptance bar described in `evals/README.md`.

- `LICENSES/CC-BY-SA-4.0.txt`, the unmodified CC BY-SA 4.0 legal code.
- Tooling: `scripts/render_catalog.py` with `--check`, catalog and ledger validation, a check that every cited AIUC-1 requirement records whether it is mandatory or optional and agrees with the requirement table in `references/frameworks.md`, `scripts/validate.py --stage DIR` to validate the installed bundle on its own, and `.github/dependabot.yml`.

### Changed

- Renamed the framework and skill from the working name RAISE to STAND (Secure, Trustworthy Agents by Non-negotiable Design) to avoid confusion with other RAISE frameworks.
- `SKILL.md` opens with the principle "The model proposes. The application enforces." and the five pillars, triages each task, routes it to catalog controls, and records results by control ID.
- `references/runtime-controls.md` and `references/verification.md` are now non-normative guidance keyed by control ID. The closed status enum replaces the earlier status vocabulary.
- `references/owasp-agentic-top-10.md` has rewritten target outcomes and adversarial evidence, and adds detection signals, page references and catalog control mappings.
- `references/frameworks.md` separates the framework basis from related OWASP projects and updates the source snapshot.
- `assets/agent-security-record.md` is keyed by control ID and uses the closed status and evidence scope enums.
- `README.md` is the front door; installation detail moved to `docs/install.md`.
- `SKILL.md` stays near the 5,000-token guideline (the validator warns slightly above it): the fail-safe defaults for missing facts moved to `references/profile-and-levels.md`, and the compact record rules to the template, with summaries left in place.
- `assets/agent-security-record.md` sets a length budget for FULL records (about 110 lines for the fixed structure, plus one per applicable control and one per Inventory entry, register operation, assumption, signal or residual risk beyond the placeholder rows), groups not-applicable controls by reason, lists inventory entries one per line, and states the compact record's counting rule. The compact record merges "Locations" into the Tier line, so the fixed lines and fences fit in 12.
- `evals/cases.json`: record lines include fences and headings and exclude required Inventory rows; a control dropped with its reason keeps its line, so the `narrow-timeout` C7 bar is 15 lines whether or not A-05 is dropped. This applies to runs after this commit.
- Change triage and scope rule: a new entry point is a FULL trigger and, unless it also changes the profile, verifies its own path and the carried-over cases rather than the whole system. The requested behavior and the smallest change that delivers it are the task; only what the request did not ask for is a product decision, and mechanisms that a routed or critical-boundary control requires on the requested feature's path (an E-06 disable switch for a new tool or MCP server, an A-21 deadline on a call the change adds, an I-24 version reference) are not. A diff that adds or alters an operation setting a redirecting value routes A-25. A wording-only edit to prompt, tool-description or template text keeps I-01 and I-04 and re-runs the row's critical-boundary cases without the untrusted-input and external-effect additions. Level 2 and 3 controls that need infrastructure the repository lacks get their application side and are otherwise planned. Step 4 verifies every routed control (SCOPED) and every implemented or carried-over control (FULL).
- Compact change record: a gap in an unchanged feature takes a "Finding:" line outside the line budget, and a record that lacks the section gets its heading at the end of the file, not counted. `evals/cases.json` excludes "Finding:" lines from record lines, for runs after this commit.
- `evals/cases.json` `new-application`: C6 requires the billing email and target account to come from a structured console field or the system of record, never from free-text chat, documents or tickets; new criterion C10 (A-25 verification of billing-email changes) and probes P8 to P10 (planted billing email, model-invented address, confirmation from a session that never received the preview). C6 results before and after this change are not comparable.
- `scripts/validate.py` checks the catalog counts stated in `README.md`.
- License: documentation and data (`SKILL.md`, `README.md` and the other Markdown files at the repository root, `references/`, `assets/`, `agents/`, `docs/`, `catalog/`, and the text and data in `evals/`) are now licensed under CC BY-SA 4.0, except the Developer Certificate of Origin 1.1 text quoted in `CONTRIBUTING.md`, which is reproduced verbatim under its own terms. Earlier commits remain available under the MIT license. Code (`scripts/`, `tests/`, `.github/` and repository configuration files) stays under MIT. The OWASP-derived file stays under CC BY-SA 4.0 with its attribution. `LICENSE` keeps the MIT text with an updated scope paragraph. `THIRD_PARTY_NOTICES.md` adds a per-path licensing summary, corrected OWASP attribution, the AIUC-1 citation boundary and a trademark notice.

### Security

- Closed a design gap in the earlier guidance: it had no rule against untrusted content choosing recipients, destinations or consequential arguments that the caller is allowed to use. A-06, A-07, A-08, I-01 and I-02 now cover it, and all five are in the critical-boundary set.
- Values that cross a verified separation boundary (I-02) stay untrusted-derived: A-06 and A-07 also apply through a `separation-pattern+external-effect` alternative, so a well-formed value the attacker chose (another tenant's order ID, a planted address) is still checked at dispatch. A system-of-record trusted source for an object identifier is scoped to the principal or case the run acts for (R-05, A-06), so an identifier that merely exists does not match. Sensitive data now propagates between contexts like untrusted input (R-02), so the lethal trifecta cannot be split across a summarizer and a sender.
- A-24 (outbound payload checks, Level 1, critical) limits what an outbound message, comment or document carries: data a recipient or reader is not entitled to, and remote images or data-carrying links that a renderer outside the application would fetch with no click.
- A delegate's authority includes the delegating context's own ceiling in the intersection (A-15), so a grandchild cannot exceed its parent.
- A-25 (verified changes to redirecting values, Level 1, critical, in the critical-boundary set): a stored contact email or phone number, recovery channel, payout or payee account or default refund destination, webhook or callback URL, or forwarding rule that is untrusted-derived, or not already held as verified for this principal's account and the same purpose, never takes effect on in-app confirmation alone. It is verified through this principal's destination on record, or, only for a value the principal entered in a structured field, through the new destination. Completion needs a non-GET human action after fresh re-authentication on a surface browser and computer-use agents cannot see or actuate, so an agent that reads the inbox or drives a signed-in browser cannot complete it. Every change, including one to a value already on record, is audited and the previous destination notified. A model-invented redirecting value is denied. A one-time payment to a new account sets no redirecting value and stays with A-06, A-12 and A-13; A-13 cites A-25 as the Level 1 floor for stored payment destinations. Cases A-25/T1 to T7.
- A-06: a consequential value that matches no trusted source and occurs in no content the principal supplied or designated in this task (a value the model invented, or one found only by the run's own retrieval) is denied, and a confirmation cannot authorize it. New cases A-06/T9 and A-06/T10; A-06/T7 accepts denial as well as confirmation. An item that a trigger sender delivered is not content the principal designated, even when its arrival started the run, so a value found only there is denied unless it matches a trusted source.
- A-12: a confirmation is accepted only from the session to which the server rendered its preview (recorded server-side), or from another session of the approver after fresh re-authentication to which the preview is rendered again; an approval link sent by email, push or chat opens such a preview and never confirms on its own (MUST, new cases A-12/T6 to A-12/T8). The A-25 verification page is a confirmation surface under A-12. It sits in A-12 rather than A-11 because the holder of another session already has the principal's authority, so the harm is presentation integrity, rated at A-12's default severity.
- Added coverage for surfaces the earlier guidance barely addressed: MCP token handling, descriptors, local servers, sampling and elicitation (A-16, I-18, I-19, I-20), and browser and computer-use agents (I-17).
- I-27 (per-tenant kernel isolation for code execution, Level 1, high): code executed for more than one tenant never shares a kernel across tenants and runs in a fresh sandbox per tenant and session, because every principal is a potential attacker against the other tenants.
- A-06: a URL is exempt from confirmation only when it appears verbatim in a public web result whose own request passed A-06, within a per-run cap set in trusted configuration, as a credential-less GET through I-12. URLs that appear only in output reflecting model input (code-execution output, echoing tools, agent-written notes or memory), and capability links in the principal's own mail or documents, stay consequential, and the record bounds the residual channel by the cap.
- I-12: allowlisted hosts that accept authenticated writes from any account (code hosts, registries, provider and storage APIs) are confined to the operator's account, limited to read-only methods or mirrored, so injected content cannot push context data into an attacker's account under the attacker's own token. File paths are opened relative to a trusted root handle (A-02), which closes the symlink-swap race between check and open.
- I-15: a sandbox whose workspace is later used on the host cannot write files that host tools execute (git hooks and configuration, editor tasks, `.envrc`, devcontainer and CI definitions, agent instruction and MCP configuration). A-09 and I-23 cite the rule.
- I-18: the descriptor pin covers every server-supplied field that reaches the model or the reviewer, including server instructions, tool titles, model-visible `_meta`, and prompt and resource descriptors; instructions from an unpinned server never go in system or developer position. I-01 treats pinned descriptors as trusted only while I-18 is implemented-and-verified.
- A-10: publication, sharing, sending and access grants can no longer satisfy the guard as "reversible by design". A-11 binds approvals to the requesting principal, run and step. A-18 requires a non-exportable proof-of-possession key that no model-influenced process can read.
- I-10 and A-24 cover free-text tool arguments sent to remote tool servers, and I-10 also applies through `sensitive-data+mcp`. I-02 credits context minimization only when a separate context translates untrusted content into typed values first. I-03 keeps RGI emoji tag sequences (subdivision flags) and removes every other tag sequence.
