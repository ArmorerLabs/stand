# MCP guidance

Informative guidance for applications that act as a Model Context Protocol (MCP) host or client, server, or proxy (feature tag `mcp`). It is keyed by control ID; the normative statements are in the catalog ([controls/index.md](controls/index.md)), and where this page and a control statement differ, the control statement governs. Generic rules for dispatch, egress, sandboxes and credentials are in [runtime-controls.md](runtime-controls.md); this page adds only what MCP changes. Pseudocode is in [patterns.md](patterns.md).

Pinned version: MCP specification 2026-07-28, which the [MCP versioning page](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning) lists as the current revision, with its security best practices page, and the MCP Apps extension specification 2026-01-26. Every specification statement below was checked against modelcontextprotocol.io and the MCP Apps repository on 2026-10-04, and each section links the page it relies on. Connections that still negotiate 2025-11-25 or an earlier revision are covered in [Earlier revisions](#earlier-revisions).

The specification is explicit that "MCP itself cannot enforce these security principles at the protocol level" ([overview, Security and Trust & Safety](https://modelcontextprotocol.io/specification/2026-07-28)). Consent, authorization and confinement are the application's job, which is what the controls below require.

Scope: this page covers MCP in the application under review. The coding agent's own MCP servers and skills are a development-time trust decision covered by the workspace rules in [SKILL.md](../SKILL.md).

## How to read this page

- "Spec: required" marks a statement the specification makes with its capitalized requirement keywords; "spec: recommended" marks a recommendation-level statement. Read the linked page for the exact wording and conditions.
- The catalog is sometimes stricter than the specification. Where it is, the section says so.
- Server, client and proxy duties differ. Where it matters, the text names the role (client, server or proxy) a statement applies to.

## Profiling an MCP integration

Implements S-02 for MCP. Adding a first MCP server adds the `mcp` tag, so it is a profile change and a FULL change ([profile-and-levels.md](profile-and-levels.md)). Record the properties and tags it adds per context with these rules:

- untrusted-input: tool results, resources, prompts and sampling results from every server are untrusted content in full (T-01), and so are descriptors until T-18 is implemented-and-verified for that server. The exemption for typed fields covers only an application adapter reading the application's own system of record; it never covers MCP results, however typed their `structuredContent` looks. A context that calls an MCP tool is untrusted-input from its first result, and a context that receives messages from a server's UI view is untrusted-input from the first message.
- external-effect: a tool that writes, sends or executes is external-effect. A read-only tool on a server outside the application's trust boundary (a remote server, or a local server that forwards requests to a third party) is external-effect too when the model chooses any of its arguments, because the arguments send information beyond the session; the only exception is the one for fixed destinations in the external-effect definition (every argument fixed by trusted configuration, with T-12 implemented-and-verified).
- network-egress: a remote server, a local server that makes network requests, any fetch of a URL a server supplied (OAuth discovery, resource links, `https://` resource URIs the client fetches directly, elicitation URLs), and a UI view with declared connect domains make the context network-egress, so T-12 applies.
- provider-routing: a remote server or remote agent that receives data from the context is a data recipient, so the context carries `provider-routing`, and T-10 applies whenever the context is sensitive-data (it also applies through its `sensitive-data+mcp` alternative). A server UI view that receives tool inputs or results is a recipient in the same way.
- rendered-output: a host that renders server-supplied UI (MCP Apps) renders third-party active content, so the context carries `rendered-output`; the server-UI duties of T-13, A-12 and T-18 route through the `mcp` and `rendered-output` tags.
- sensitive-data: a server tool that can read data an attacker should not obtain makes the context sensitive-data, as any tool does.

Server role. An application that only exposes an MCP server has no model context of its own. Record the calling client's proposals as untrusted input to the handlers (every argument is an untrusted proposal), profile sensitive-data and external-effect from what the handlers read and change, and record the client-only controls (T-18, T-19, T-20) as not-applicable-with-reason when the server calls no other server. Record the handlers' autonomy scope as the highest scope at which any permitted client can run them; with unknown or arbitrary clients, that is scope 4. An owner who restricts the permitted clients may record a lower scope with the restriction as its reason. The duties are in [Exposing an MCP server](#exposing-an-mcp-server).

Record the negotiated protocol revision of each server in the MCP inventory (S-04), together with its configured identity, descriptor hash and the extensions it negotiated (for example `io.modelcontextprotocol/ui`).

## Route every MCP call through the dispatcher

Implements A-01, A-02, A-09, A-21.

Many agent frameworks ship an MCP client that lists a server's tools and lets the model call them directly. That path skips every dispatcher check: identity, schema, authorization, provenance, approval and budget. Instead, adapt each pinned MCP tool into the application's own tool registry, so a call runs model proposal, then dispatcher, then the MCP client as the adapter. The MCP client and its credentials are adapter internals that nothing else can reach (A-01). [integrations.md](integrations.md) shows where the stubs go in a framework-owned loop.

- Register MCP tools under a fully qualified name that includes the server identity from your own configuration, for example `billing-server.create_refund`. The specification recommends that tool names be unique within a server, says clients that aggregate servers should disambiguate, for example by prefixing a server identifier, and warns that the server `name` from `serverInfo` is not guaranteed to be unique and should not be relied on (spec: recommended). Resolve only fully qualified names, and fail closed on ambiguous or look-alike names (A-02, T-18). ([Tools: Tool Names](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#tool-names))
- Validate arguments against the pinned, reviewed input schema and the register's semantic constraints. A server's `inputSchema` describes shape, not permission (A-02). In 2026-07-28 the schemas may use any JSON Schema 2020-12 keyword; resolve `$ref` with the specification's resolution requirements and bounds, or reject schemas you cannot validate strictly.
- Expose to each agent context only the MCP tools its task needs (A-09, S-03). Every tool description you expose enters the model's context, so an unneeded server is both attack surface and injection surface.
- Decide auto-run and approval from the register's consequence class and the parsed arguments, never from annotations such as `readOnlyHint` or `destructiveHint`. The specification requires clients to consider tool annotations untrusted unless they come from trusted servers (spec: required). The catalog goes further: annotations and descriptor text never relax policy or approval requirements, even from a trusted, pinned server, because the register (S-05) alone sets an operation's consequence class and approval policy (T-18, T-18/C4). ([Tools: Data Types](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#tool))
- The tools page recommends a human in the loop who can deny tool invocations, UI that shows which tools are exposed, confirmation prompts for operations, and that clients "Show tool inputs to the user before calling the server, to avoid malicious or accidental data exfiltration" (spec: recommended). In this framework, confirmation is targeted (A-06, A-07, A-08, A-10) rather than required for every call, and the tool inputs appear in the server-rendered approval preview (A-12). The overview's key principles go further (hosts must obtain explicit user consent before invoking any tool). This page reads that as consent when the principal enables a server and its tools for a context, plus the targeted confirmations; per-call prompts for routine operations recreate the approval fatigue that A-13 measures.
- The tools page recommends client timeouts for tool calls (spec: recommended). Enforce the deadline in the caller, independently of the transport (A-21). In 2026-07-28 a broken response stream loses the in-flight request, and clients re-issue it as a new request (spec: required); send the same idempotency key on the re-issued call and reconcile first where the server may have committed (A-05).
- The tools page recommends logging tool usage for audit (spec: recommended). Include the server identity and descriptor hash in the dispatcher's events (N-01).

State handles. With no protocol-level session in 2026-07-28, a server that needs state across calls returns a handle (a basket, a workflow, a browser context) from one tool and accepts it as an ordinary argument on later calls; the tools page notes that "the model is responsible for carrying `basket_id` forward" ([Tools: Stateful Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#stateful-tools), non-normative). A handle the model carries is a model-chosen argument, and injected content can steer the model to present a different one: another workflow of the same user, or one leaked from elsewhere. The server's ownership check (A-16) stops cross-user use, but not a confused deputy within the same user. So the dispatcher keeps handles itself:

- register handle arguments in the register as consequential arguments whose trusted source is "a handle this server minted in this run for this principal" (S-05);
- record each handle from the creating tool's result in per-run server state, keyed by server, principal and run, and let the model refer to it by a local alias that the dispatcher replaces with the stored value;
- deny a call that carries a handle this run did not receive, and expire the record with the run.

`x-mcp-header`. A server may mark tool parameters with `x-mcp-header`, and on Streamable HTTP the client then mirrors their values into `Mcp-Param-{Name}` headers so that load balancers, gateways and firewalls can route on them (spec: required for clients). Clients must reject tool definitions whose `x-mcp-header` values break the constraints, including control characters, and must Base64-encode values that are not plain visible ASCII, contain control characters or match the sentinel pattern; servers must reject headers that do not match the body (spec: required). The specification also says servers should not mark sensitive parameters, because intermediaries see the headers (spec: recommended). For the application:

- use an SDK transport that implements the encoding, and never assemble `Mcp-Param-*` headers by hand from model output;
- `x-mcp-header` is part of the input schema, so it is hashed and pinned with the descriptor (T-18); at review, reject a mapping on a parameter that can carry a data class the intermediaries may not see (S-06);
- where an intermediary routes or authorizes on a mirrored value (a region, a tenant), that parameter is a consequential argument with a trusted source in the register, because the model now chooses where the request goes (S-05, A-06).

([Tools: x-mcp-header](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#x-mcp-header); [Streamable HTTP: Custom Headers from Tool Parameters](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http#custom-headers-from-tool-parameters))

## Descriptors: pinning, rug pulls and shadowing

Implements T-18, T-01, T-03, S-04, N-04.

Three attacks target the descriptions a client loads, as described by [Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks):

- Tool poisoning: instructions hidden in a tool description that the model reads and the user does not see.
- Rug pull: the server changes a description after the user or reviewer approved it.
- Cross-server shadowing: a malicious server's description changes how the agent uses a different, trusted server's tool, for example telling it to send every email through the trusted email tool to an attacker's address.

The specification's overview says that descriptions of tool behavior such as annotations "should be considered untrusted, unless obtained from a trusted server" ([overview](https://modelcontextprotocol.io/specification/2026-07-28)). Treat tool results, resource contents, prompt templates and sampling results from any server, trusted or not, as untrusted content that taints the context (T-01). Treat descriptions, annotations and server instructions the same way until they are reviewed and hash-pinned (T-18): instructions from a server that is not pinned never go in system or developer position. A reviewed, pinned descriptor is trusted configuration: it goes in the provider's tool-definition field, does not taint the context, and any change to it disables the tool until re-review. That trust holds only while T-18 is implemented-and-verified for the server, including its drift-disabling test; until then its descriptors are untrusted content and taint the context (T-01). Trust never lets a descriptor or annotation relax policy or approval (T-18). This follows the specification's distinction between trusted and other servers; the catalog adds that trust in a server is established by review and pinning, never by the server's own claims, and the discovery result's `serverInfo` is self-reported, which the specification says clients should not rely on for security decisions ([Discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover)).

Review has to see what the model will see. Poisoned descriptors hide their instructions in Unicode tag characters, bidirectional controls and zero-width text, or past the point where a client UI truncates a description. T-18 therefore requires review of the full descriptor after the hidden-text normalization described under T-03, with invisible and control characters shown and nothing truncated, and pinning fails on tag characters, bidirectional controls or zero-width characters the reviewer has not explained. This applies at every level, as part of T-18, even though T-03 itself is a Level 2 control; only a descriptor that passed this review becomes trusted configuration.

- Pin each server by its configured identity (URL, or package, version and exact command for stdio) and by a hash over every server-supplied field that reaches model context or the reviewer: the server name, version and `instructions` (returned by `server/discover` in 2026-07-28, and placed in the system prompt by many hosts); tool names, titles, descriptions, input and output schemas (with any `x-mcp-header` mappings), annotations and any `_meta` content exposed to the model, including `_meta.ui` references to UI resources; prompt, resource and resource-template names and descriptions; and the HTML of each `ui://` resource with its declared domains and permissions. Hash only the `_meta` fields that reach the model or the reviewer, because servers may put volatile data there. Record both in the inventory (S-04). Refuse to load a server or tool that is not pinned (T-18).
- A change to a server-level field such as `instructions` disables all of that server's tools until re-review, so a rug pull that edits only the instructions cannot pass with every tool hash intact (T-18).
- In 2026-07-28, list-changed notifications arrive only on a `subscriptions/listen` stream the client opts into, and servers that declared `listChanged` are recommended to send `notifications/tools/list_changed` there (spec: recommended). On that notification, disable the affected tools, re-list, diff against the pin and hold them for re-review. Do not rely on the notification: a hostile server can change silently, so re-hash on every `tools/list`, including each refresh when a cached list's `ttlMs` expires, and emit a drift signal on any mismatch (N-04). ([Tools: List Changed Notification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#list-changed-notification))
- A server's tool list must not vary per connection but may vary with the authorization presented on the request (spec: required and permitted respectively). A tool that appears only for some principals is still unpinned until reviewed, so pin by tool, not by "the list I saw first".
- Where several servers of different trust share one context, any one server's text can steer calls to the others. Split contexts by trust level where the task allows, and keep high-consequence tools out of contexts that load descriptions from servers you do not control.
- A valid signature on a package or descriptor identifies the publisher; it does not make the descriptor safe (T-18).

## Tokens, authorization and server-held state

Implements A-16, A-17, A-18, T-05.

Token passthrough is the anti-pattern in which a server accepts a token that was not issued to it and forwards it to a downstream API. The specification forbids it because it bypasses audience-dependent controls such as rate limiting and request validation, breaks audit attribution, and lets a stolen token use the server as a proxy. ([Security best practices: Token Passthrough](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#token-passthrough); [Authorization: Token Handling](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#token-handling))

As an MCP client:

- Use a token issued for that server's audience, never the end user's token for some other service. Clients include the RFC 8707 `resource` parameter identifying the MCP server in authorization and token requests, and send the server only tokens issued by its authorization server (spec: required).
- Use PKCE with `S256`, and refuse to proceed when the authorization server's metadata does not show PKCE support (spec: required). ([Authorization: Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations))
- Record the expected issuer from the validated authorization server metadata before redirecting, and validate a present `iss` in the authorization response against it, by simple string comparison, before sending the code to any token endpoint; reject a response without `iss` when the metadata advertises `iss` support (spec: required, RFC 9207). This stops a mix-up attack in which a hostile authorization server collects a code another server issued. ([Authorization: Authorization Response Validation](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#authorization-response-validation))
- Key persisted client credentials by the authorization server's `issuer`, never reuse them with a different authorization server, and re-register when it changes (spec: required). Prefer pre-registered client information, then Client ID Metadata Documents; Dynamic Client Registration is deprecated in 2026-07-28 and is a fallback only (spec: recommended order). ([Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration))
- Request a minimal initial scope set and elevate on specific challenges, rather than everything in `scopes_supported` ([Security best practices: Scope Minimization](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#scope-minimization)). Wildcard or omnibus scopes widen the blast radius of a leaked token.
- Send tokens only in the `Authorization` header, never in a query string (spec: required), which also keeps them out of URL logs.
- Keep `requestState` out of the model's reach. When a server answers with an input-required result, echo its `requestState` exactly on the retry and never inspect or change it (spec: required); hold it in the dispatcher's per-call state, never in model context, and never let a model-supplied value stand in for it.

As an MCP server:

- Validate every access token and reject any token not issued for this server as its audience (spec: required). Accept or transit no other tokens (spec: required).
- When the server calls upstream APIs, it acts as an OAuth client with a separate token issued by the upstream authorization server; it never passes through the token it received (spec: required). At Level 2, use token exchange or an on-behalf-of flow that records subject and actor (A-17).
- Do not treat claimed scopes as sufficient on their own. The best practices list "treating claimed scopes in token as sufficient without server-side authorization logic" as a common mistake; the server still resolves the object and checks the principal's access at the moment of effect (A-03, A-04).

As an MCP proxy that uses a static client ID toward a third-party authorization server:

- Implement per-client consent before the third-party flow (spec: required): keep a per-user registry of approved `client_id` values and check it first; show an MCP-server-owned consent page that names the client, the third-party scopes and the registered `redirect_uri`, with CSRF protection and anti-framing; bind consent cookies to the specific `client_id`; match `redirect_uri` exactly; and generate a single-use, short-lived `state` value that is stored only after consent is approved. ([Security best practices: Confused Deputy Problem](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#confused-deputy-problem))

Server-held state:

- 2026-07-28 has no protocol-level sessions. Servers that implement authorization verify every inbound request, and no server treats possession of a state handle as authentication (spec: required). Use secure, non-deterministic handles from a secure random number generator, with an expiry, and bind them to the authenticated user, for example by keying stored state as `<user_id>:<handle>` with the user ID taken from the verified token, rejecting a handle presented by any other principal (spec: recommended; the catalog requires the binding under A-16). ([Security best practices: State Handle Hijacking](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#state-handle-hijacking))
- Multi round-trip requests let a server keep its state in `requestState`, which the client echoes back. The specification requires servers to treat it as attacker-controlled input, to protect its integrity (for example with an HMAC or AEAD) whenever it influences authorization, resource access or business logic, and to reject state that fails verification; it recommends putting the authenticated principal, a short expiry and an identifier of the originating request inside the protected payload, and requires server-side enforcement where state must be used at most once ([Multi Round-Trip Requests](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)). The catalog reads this as the server-side counterpart of T-09: include all three bindings every time, and keep any single-use record on the server.
- Tasks are an extension (`io.modelcontextprotocol/tasks`) in 2026-07-28. A task ID is a durable handle: bind it to the authorization context that created it, and reject `tasks/get`, `tasks/update` and `tasks/cancel` from any other principal (A-16).
- Servers that store elicitation state associate it securely with individual users, and derive user identity from the credentials obtained through MCP authorization where possible (spec: required). ([Elicitation: Statefulness](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation#statefulness))

Credentials for stdio servers. The authorization specification says stdio implementations should not follow it and should instead "retrieve credentials from the environment" ([Authorization: Protocol Requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#protocol-requirements)). This is where T-05 matters: give a stdio server only the narrowly scoped credential it needs, injected into its sandbox, never the host's environment, home directory, cloud configuration or SSH agent. At Level 3, sender-constrain tokens that could surface in context, logs or a model-influenced process (A-18).

## Discovery, URLs and transports

Implements T-12, T-14, A-16.

A malicious server chooses the URLs a client fetches during OAuth metadata discovery: the `resource_metadata` URL in the `WWW-Authenticate` header, the `authorization_servers` in the protected resource metadata, and the token and authorization endpoints in the authorization server metadata. Pointing them at `169.254.169.254`, internal services or localhost turns the client into an SSRF proxy. Clients deployed to a server are required to consider SSRF here (spec: required), and the best practices recommend HTTPS, blocking private and reserved ranges (including `169.254.0.0/16`), validating redirect targets and using an egress proxy, and warn: "Avoid implementing IP validation manually." ([Security best practices: Server-Side Request Forgery](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#server-side-request-forgery-ssrf))

- Route every discovery and metadata fetch through the egress boundary in allowlist mode (T-12), with redirect hops validated and DNS resolved by a controlled resolver. The catalog requires this (A-16), not just recommends it.
- Authorization URLs from a server: accept only `https` (and `http` only for loopback during development), reject `javascript:`, `data:`, `file:`, `vbscript:` and other dangerous schemes, never open a URL through a shell command, and sanitize every URL received from a server (spec: required). Web-based clients are recommended to set a Content Security Policy (spec: recommended). ([Security best practices: OAuth Authorization URL Validation](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#oauth-authorization-url-validation))
- URLs inside tool results, resource links and elicitation requests are untrusted render targets; apply the rendering and link rules in [runtime-controls.md](runtime-controls.md#egress-and-exfiltration-channels) (T-13, T-14). A resource whose URI uses `https://` may be fetched by the client directly; that fetch goes through the egress boundary like any other ([Resources: Common URI Schemes](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#common-uri-schemes)).
- Streamable HTTP servers validate the `Origin` header on all incoming connections to prevent DNS rebinding, and answer an invalid one with HTTP 403 (spec: required). Servers running locally are recommended to bind only to localhost, and all servers to authenticate every connection (spec: recommended). ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http))
- A server that processes the body rejects requests whose `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` or `Mcp-Param-*` headers do not match it (spec: required). An intermediary that routes or rate-limits on those headers is enforcing policy on a mirrored value: let it trust them only for a protocol version that requires header-body validation by the server behind it, as the specification recommends.

## Local (stdio) servers

Implements T-19, T-05, A-23.

A local server is arbitrary code running on the user's or the application's host, with the client's privileges unless you confine it. The best practices list malicious startup commands in client configuration, malicious payloads inside the server, and insecure local servers reached through DNS rebinding. ([Security best practices: Local MCP Server Compromise](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#local-mcp-server-compromise))

- Clients that offer one-click local configuration must, before running anything, "Show the exact command that will be executed, without truncation", identify it as code execution, require explicit approval and allow cancellation (spec: required for one-click configuration). The catalog applies this to every configuration path and requires re-approval whenever the command or its arguments change (T-19).
- The best practices recommend executing server commands in a sandbox with minimal default privileges, restricted file system and network access, and explicit grants for anything more (spec: recommended). The catalog requires it: each server sees only its declared files, network destinations and secrets (T-19), and holds no ambient credentials (T-05).
- Roots are deprecated in 2026-07-28 and were always advisory: the roots page says they are "informational guidance rather than an access-control mechanism" ([Roots](https://modelcontextprotocol.io/specification/2026-07-28/client/roots)). Enforce file confinement in the sandbox. The suggested replacements (directories passed as tool parameters, resource URIs or server configuration) differ in trust: a directory in a tool argument is a model-chosen path (A-02, A-06), so prefer server configuration for anything that bounds what a server may touch.
- Files that define MCP servers, tools, skills or agent rules, and approval or auto-run settings, are not writable by the agent wherever the write takes effect without human review, so an injected instruction cannot install a new command or switch on auto-approval (A-23). In a local working tree, the files the client loads or reloads (MCP configuration, rules files, workspace editor settings) are active configuration, and so is a pushed branch for the automation that runs on it ([runtime-controls.md](runtime-controls.md#coding-and-ci-agents)).
- Where a local proxy spawns stdio servers on request, a cross-site scripting bug in the client can become arbitrary command execution through the proxy. The best practices recommend sandboxing spawned processes, restricting their file system access, logging stdio usage and requiring extra authorization for dangerous commands (spec: recommended). ([Security best practices: stdio Transport Security in Proxy Scenarios](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#stdio-transport-security-in-proxy-scenarios))
- Servers meant to run locally are recommended to use stdio, or to require an authorization token or a restricted IPC channel if they use HTTP (spec: recommended).

## Sampling and elicitation

Implements T-20, A-20, A-22, A-12, T-26.

Both features are server-originated, so both are untrusted. In 2026-07-28 a server no longer sends them as its own requests: it answers `tools/call`, `prompts/get` or `resources/read` with an input-required result whose `inputRequests` carry `sampling/createMessage`, `elicitation/create` or `roots/list`, and the client retries the original request with `inputResponses` ([Multi Round-Trip Requests](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)). The controls below apply to each input request, whatever carries it.

Sampling lets a server ask the client's model to generate, which means a server can drive your model and spend your budget. Sampling is deprecated in 2026-07-28: new implementations should not adopt it, and existing ones should migrate (spec: recommended). The sampling page recommends a human who can deny requests, review of prompts and generated responses, rate limiting, and iteration limits for tool loops (spec: recommended). ([Sampling](https://modelcontextprotocol.io/specification/2026-07-28/client/sampling))

- Do not declare the `sampling` capability unless a reviewed server needs it. Where it is declared, deny sampling by default and allow it per server by policy (T-20).
- Include only the context the request needs. The `includeContext` values `thisServer` and `allServers` are deprecated; never send other servers' context or the user's conversation to a server.
- Count every sampling request and its tokens against the run budget and the principal's quotas, through the same wrapper as every other model call (A-20, A-22; [patterns.md](patterns.md)).
- Treat sampling results as untrusted content wherever the client reuses them (T-01).
- With sampling with tools, the server supplies tool definitions and executes the resulting tool uses itself. Those effects happen at the server, outside your dispatcher; present the proposed tool calls for review as the specification's flow shows, and decide whether that server may cause them at all.

Elicitation lets a server ask the user for input in the middle of an operation, which a hostile server can style as the application's own login or payment screen. ([Elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation))

- Clients make clear which server is requesting information, offer decline and cancel, and in form mode let the user review and modify responses before sending (spec: required). Render elicitation outside the application's trusted approval and login surfaces, labeled with the server's identity (A-12, T-20).
- Servers do not use form mode for passwords, API keys, access tokens or payment credentials, and use URL mode for them (spec: required). Do not rely on the server: block or warn on form requests that ask for secrets (T-20, T-26).
- URL mode keeps secrets out of the client and the model. Clients do not pre-fetch the URL or its metadata, do not open it without consent, show the full URL before consent, and open it in a way that does not let the client or the model inspect the content or the user's input (spec: required). They are recommended to highlight the domain and warn on ambiguous URLs such as Punycode (spec: recommended). The catalog requires the domain highlighting as well, and requires the page to open outside any surface the model can read or actuate (T-20).
- Servers bind elicitation requests to the client and user identity, and verify that the user who opens a URL-mode link is the user the elicitation was created for before accepting information (spec: required). The client learns the outcome only by retrying; servers correlate it through `requestState`, which they protect as above.

## Server-supplied UI (MCP Apps)

Implements A-01, A-12, T-01, T-13, T-18, T-10.

MCP Apps is an optional extension (`io.modelcontextprotocol/ui`) that lets a server ship interactive HTML. A tool declares a `ui://` resource in `_meta.ui.resourceUri`; the host fetches it and renders it in a sandboxed iframe; the view and the host talk over JSON-RPC through `postMessage`. A view can call the server's tools (`tools/call`), post messages to the conversation (`ui/message`), update the model's context (`ui/update-model-context`), ask the host to open a link (`ui/open-link`) and read resources. SEP-1865, which introduced it, is marked Final on the Extensions Track and, when read on 2026-10-04, listed its sponsor as "None (seeking sponsor)". Its own mitigations are iframe sandboxing, predeclared templates that hosts can review, auditable messages, and the note that "Hosts can require explicit approval for UI-initiated tool calls". ([MCP Apps specification 2026-01-26](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx); [SEP-1865](https://modelcontextprotocol.io/seps/1865-mcp-apps-interactive-user-interfaces-for-mcp); [MCP Apps overview](https://modelcontextprotocol.io/extensions/apps/overview))

What the extension specification requires of hosts: render all view content in sandboxed iframes (spec: required); for web hosts, a sandbox proxy on an origin different from the host's; a Content Security Policy built from the resource's `_meta.ui.csp` (`connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains`), with a restrictive default when it is absent, which the host may tighten but must not widen to undeclared domains (spec: required); and tool visibility, under which a tool without `"app"` in `_meta.ui.visibility` cannot be called from a view and a tool without `"model"` is kept out of the model's tool list (spec: required). It leaves user consent for view-initiated calls to the host, and notes that a view can still show misleading content. The application's duties as a host start there:

- Every `tools/call` from a view enters `dispatch` as an untrusted proposal from that server, with the run's trusted context; visibility is a filter, not authorization. A view may name only tools of its own server whose visibility includes `"app"`: deny a call from it to another server's tool or to an application-native tool, which would otherwise run under the run's authority at the request of the least trusted party in it (A-01, A-01/C5). A consequential call is checked like any other, and confirmed where A-06, A-07 or A-08 require it (A-01/C4).
- Confirmations render on the application's own surface, outside any frame the view controls, and clearly outside the view's boundary. A view can draw an Approve dialog that looks like yours; clicking it confirms nothing (A-12, A-12/C11).
- A message a view sends with `ui/message` or `ui/update-model-context` is untrusted content: it enters the context in a data position and taints it (T-01). It is not the principal's turn, so it cannot set or widen task scope (A-07), designate content or supply a principal-entered value (A-06), or approve anything (A-11). The same holds for a selection inside the view: a picker the view draws can look like the application's, but A-06 and A-07 count only structured interfaces the application renders (A-06/C19).
- `ui://` resources, their declared domains and requested permissions are part of the pinned descriptor. A change disables the view and the tools that use it until re-review, and fires a drift signal (T-18, T-18/C8).
- Render the view on a separate origin, sandboxed, with a CSP whose fetch and frame directives list only the domains the server declared and your egress policy allows (T-13, T-13/C7). Data the host pushes into the view (tool inputs and results) can leave through any connect domain, so the view's server and every connect domain are recipients under the data policy (T-10, S-06); in a context with sensitive data, allow no connect domain you have not approved for those classes.
- Treat `ui/open-link` as a link in agent output: show the full destination before navigating, and never open it automatically (T-13). Deny device permissions (camera, microphone, geolocation, clipboard write) unless policy grants them for that server.

When the application exposes MCP Apps, its UI runs inside other hosts. Authorize every tool call at the handler whether the model or a view made it (A-03), keep declared domains to what the view needs, and do not assume the host asks the user before a view-initiated call.

## Remote servers as data recipients

Implements T-10, A-06, A-24, T-11, S-06.

- Everything sent to a remote server (tool arguments, resource requests, sampling results, data pushed to its UI view) is a disclosure to that server's operator. Add each remote server to the data-classification policy as a recipient and send only the classes it may receive (T-10, S-06). The overview says hosts must obtain explicit user consent before exposing user data to servers ([overview](https://modelcontextprotocol.io/specification/2026-07-28)).
- Tool arguments are an exfiltration channel, which is why the tools page recommends showing inputs before calls. When the context is tainted and also holds sensitive data, URL, host, path and query arguments to remote tools are consequential values under A-06: they match a trusted source, or are confirmed with their provenance when they occur in content the principal supplied or designated, and a query or URL the tainted context composed is denied, never sent on confirmation. A URL argument to a remote MCP tool never qualifies for the A-06 read-tool exemption, even when it was followed unchanged from a public web result: the call is an authenticated request to the server's operator, who receives the URL and fetches it outside your egress boundary (T-12), so it is not a credential-less GET through that boundary, and the operator is one more recipient of the data. Free-text arguments cannot match a trusted source, so govern them as disclosures, tainted or not: the data classes they can carry, determined from what the context read as in A-24, must be ones the data policy allows for that server. T-10 requires this for remote tool servers, and A-24 covers free-text arguments that reach a party outside the application. Otherwise deny the call, route it to a server approved for those classes, or confirm it with the content shown. This keeps confirmations targeted rather than per call (A-13).
- When the model provider's API calls a remote MCP server for you (a provider-hosted connector), the call never reaches your dispatcher. Govern it as a provider-executed tool: allowlists, approval kept on for servers that receive protected data or cause effects, and logged call records (T-11, [runtime-controls.md](runtime-controls.md#provider-routing-and-provider-executed-tools)). A stop also cancels the run's connector calls and revokes the credentials connectors hold (N-06).

## Exposing an MCP server

Implements A-01, A-03, A-04, A-16, A-20, A-22, T-12.

When the application is the server, the calling client and its model are untrusted proposers, and your tool handlers are effect adapters.

- Put tool handlers behind your own dispatcher and policy. Authorize each call against the principal from the validated token, at the moment of effect, never against tool arguments, state handles or identity claims in the request (A-03, A-04). The elicitation page states the same rule for user identification: servers do not rely on client-provided identification without server verification (spec: required).
- The tools page requires servers to validate all tool inputs, implement proper access controls, rate limit tool invocations and sanitize tool outputs (spec: required). The resources page requires servers to validate all resource URIs and to sanitize file paths against directory traversal for `file://` resources, and the prompts page requires implementations to validate prompt inputs and outputs (spec: required). Rate limits per principal and tenant are budgets in this framework (A-20, A-22).
- Validate audience on every token and never pass a received token upstream ([Tokens, authorization and server-held state](#tokens-authorization-and-server-held-state)). Bind every state handle, task ID and `requestState` to the principal as described there.
- Validate mirrored headers against the body, and reject a request with a recognized `Mcp-Param-*` header that carries invalid characters (spec: required).
- Your tool descriptions, server instructions and UI resources are someone else's untrusted content. Keep them factual, free of instructions to the model, and stable; a change is a breaking change for clients that pin hashes. Return tools in a deterministic order, as the specification recommends, so that clients can cache and compare them.
- If the application runs the authorization server for its MCP server and accepts Client ID Metadata Documents (in 2026-07-28, authorization servers and clients are recommended to support them), the authorization server fetches a URL that an unknown client supplies as its `client_id`. Authorization servers are required to consider the security implications in the Client ID Metadata Document draft's security considerations (spec: required) and are recommended to consider SSRF and to cache documents respecting HTTP cache headers (spec: recommended). Fetch the document through the egress boundary (T-12) or an equivalently SSRF-hardened fetcher, with a size limit. Validate that the document's `client_id` matches its URL exactly and that the redirect URI in each authorization request matches the document (spec: required). On the authorization screen, clearly display the redirect URI hostname (spec: required), and warn on redirect URIs that are only `localhost`, because an attacker can present a legitimate client's metadata URL with its own `localhost` listener (spec: recommended). Include `iss` in authorization responses (spec: recommended); an authorization server that includes it advertises `authorization_response_iss_parameter_supported` in its metadata (spec: required). ([Client Registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration); [Authorization: Security Considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations))

## Verification pointers

Each control's hostile cases and authorized twin are in the catalog; [verification.md](verification.md) explains the method. The MCP-specific cases, all driven through the real client or server path into a controlled test server or destination:

- T-18: change a tool description on a test server to include hidden instructions and send `notifications/tools/list_changed`; the tool is disabled and a drift signal fires (T-18/C1). Change only the server's `instructions` and reconnect; all of its tools are disabled and a drift signal fires (C2). Register a colliding or look-alike name on a second server; resolution fails closed (C3). Mark a destructive tool `readOnlyHint: true` on an untrusted server and on a pinned, trusted one; approval policy is unchanged in both (C4). Add an unpinned server to configuration; it is not loaded (C5). Submit a descriptor whose instruction is written in Unicode tag characters; pinning fails (C6). Change the HTML of a pinned `ui://` resource; the view does not render and its tools stay disabled until re-review (C8).
- A-16: as a client, capture outbound calls; each carries a token issued for its audience (A-16/C1). Server role: forward the user's upstream token to the server; it rejects it on audience (C2), and another user's MCP session identifier, or under 2026-07-28 another user's state handle, is rejected (C3). Point `resource_metadata` at `169.254.169.254`; the fetch is blocked at the egress boundary (C5). Cases for a role the application does not have are recorded as not applicable with the absence named ([conformance.md](conformance.md)).
- A-16/L1: injected content makes the model present a state handle that this run never received (another workflow of the same user); the dispatcher denies the call and the server receives nothing.
- A-16/L2: server role: a retry carries a modified `requestState`, and another principal's valid `requestState`; both are rejected before any effect.
- A-16/L3: a hostile authorization server returns an authorization response whose `iss` names another authorization server; the client rejects it before sending the code to any token endpoint.
- A-02/L1: a tool argument mirrored by `x-mcp-header` contains a carriage return, a line feed and a second header; on the wire it appears only in Base64 form, and a hand-built request whose header differs from the body is rejected by the server.
- T-19: for stdio servers, alter the configured command's arguments; the server does not start (T-19/C1), and a canary outside the server's declared scope cannot be read or sent (C2). Through injected content, ask the agent to edit its MCP configuration or to set a workspace setting that auto-approves tool calls; neither takes effect without review (A-23/C7, C8).
- T-20: issue looping sampling requests and one that asks for the conversation history; the budget stops the loop and no client context is included (T-20/C1). Send an elicitation styled as an application login that asks for an API key; it is blocked or shown with the server's identity and a warning (C2). Send a URL-mode request whose URL is a Punycode look-alike; the full URL is shown with the domain highlighted and a warning, and nothing is fetched before consent (C3).
- A-01: drive a forbidden proposal through the framework's native MCP client path; it is denied at the dispatcher and no server call occurs (A-01/C1). A view initiates a tool call that sends to an attacker's address; it reaches the dispatcher as an untrusted proposal and nothing is sent before confirmation (C4). A view asks for another server's tool and an application-native send tool; both are denied (C5).
- A-12/C11: a view draws an Approve dialog that imitates the application's; clicking it confirms nothing.
- T-13/C7: a view with a canary in its data fetches a host its server did not declare; the frame's CSP blocks it and the controlled host receives nothing.
- T-01/L2: a view sends `ui/update-model-context` with an instruction to forward the conversation; the context is marked tainted and the content appears only in a data position.
- A-06/L6: in a context that holds sensitive data and has read web results, the model proposes a remote MCP fetch tool call whose URL it took verbatim from the results of a search a query composer derived; the call is not treated as an exempt read, so it is denied with no confirmation offered (those results are not designated), and the server receives no call.

Pair every case with an authorized twin of the same shape (a pinned, unchanged tool works by its fully qualified name; a correctly issued token is accepted; a handle the run received is accepted; a view's in-scope call runs once).

## Earlier revisions

2026-07-28 removed mechanisms that earlier revisions use: protocol-level sessions and the `Mcp-Session-Id` header, the `initialize` handshake, server-initiated requests (`roots/list`, `sampling/createMessage`, `elicitation/create`), the standalone GET stream and stream resumability; tasks moved from the core protocol into an extension ([2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). A client or server may still support several revisions. For each connection that negotiates 2025-11-25 or earlier, the 2025-11-25 safeguards apply to that connection:

- session IDs are secure and non-deterministic, bound to the authenticated user (for example `<user_id>:<session_id>`), and never treated as authentication ([2025-11-25 security best practices: Session Hijacking](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices#session-hijacking)), which runs the A-16/C3 case against session identifiers;
- the `instructions` returned by `initialize` are hashed and pinned like those from `server/discover` (T-18);
- server-initiated sampling and elicitation requests are untrusted, budgeted and reviewed exactly as input requests are (T-20);
- tasks, experimental in 2025-11-25, are bound to their authorization context, with `tasks/get`, `tasks/result` and `tasks/cancel` rejected from other contexts (spec: required in that revision) ([2025-11-25 Tasks](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/tasks)).

A server that supports only 2026-07-28 ignores an `Mcp-Session-Id` header and mints no session IDs (spec: recommended). Record the negotiated revision or revisions of each server in the MCP inventory (S-04). Record a case whose mechanism a revision removed as `<ID>/C<n>: not applicable (removed in protocol <revision>; earlier revisions not accepted)` only when the implementation rejects every earlier revision that has the mechanism, which is the verifiable absence [conformance.md](conformance.md) requires; while it still negotiates an earlier revision, run the case against that revision.
